# 统一发布、启动和升级验收

日用实例已接管到 `.data/control-plane`，启动、升级、恢复、状态及 MCP 共同读取一个 `installation.json`。固定入口不包含日期版本路径，完整包副本在 `versions`，数据代次在 `generations`，一致备份在 `backups`；原私有数据、原包与已有任务工作树保留。

## 已实现

- `scripts/publish.mjs` 作为构建端入口，串起现有依赖上的 TypeScript 构建、全量测试、可选 Hermes 构建、Windows 打包、原生 SQLite/迁移探针及全包逐文件校验。未运行依赖安装或下载。
- 包内“打开工作台”准备独立安装目录和随包 Node；安装后的中文入口及本机根目录快捷入口均转发固定引导器。旧启动器只保留兼容转发。
- 升级在新目录准备与验证数据，原数据代次不覆写；仅在备份、恢复、健康身份和连续性检查完成后开放写操作。维护期间网页历史 GET 可读，HTTP 写请求暂缓，启动认证延后到维护完成。
- 故障日志、备份与版本副本保留。未验证的升级回到旧代次；已验证但中断的提交继续完成，不回到可能过时的数据库。显式恢复确认原维护进程已退出，保留不明锁和身份，不杀进程或直接删除引擎 `instance.lock`。
- 客户端连接只在初次接管时改后台启动描述，令牌、授权工具和项目范围保持。宿主 Codex `config.toml` 完整 SHA-256 与接管前相同。

## 验证

1. 新增 9 项确定性测试，覆盖备份后独立代次提交、活跃任务拒绝、备份/恢复/验证失败回退、无法确认停止时保留恢复记录、维护进程中断与已验证提交续接、版本验证及网页维护闸门。统一发布入口完成 805 项全量回归与原生 20 迁移打包探针。
2. 独立安装、独立端口的实际后台服务完成重复启动与正常代次升级。随后使用一个文件清单自洽、但启动入口确实抛错的故障包：恢复副本已准备而新版启动失败，管理器自动重新选择并启动原版。原任务、真实 PNG/文字字节、连接与客户端授权相同；故障包、日志和备份保留。该过程不调用模型。
3. 日用实例完成从历史入口的空闲接管及后续统一升级。升级前后 70 个任务、71 次执行、112 条审批与 5 份已绑定输入文件相同，原未合并 `mcp-input.html` 的 SHA-256 相同。每次升级检查项目策略、全局代理、授权文件及任务/附件投影连续性。最后逐个重新读取 5 份原附件并核对字节 SHA-256。
4. 后续升级前后，对 5 个中文启动管理脚本、固定 MCP 桥、私有连接和宿主 Codex 配置做逐字节哈希比较，全部相同。后续发布只选择完整包，不再修改多个脚本或宿主配置。
5. 实际停机后的 Codex 查询发现冷启动缺陷：直连 loopback 返回顶层 `code=ECONNREFUSED`，生命周期只读取 `cause.code`，因此没有启动后台。已兼容两种错误，补直接错误等待与真实 loopback HTTP 的两项回归；相关 15 项测试通过。
6. 部署修复后，真实 SDK stdio 客户端通过既有固定 MCP 入口，从停机状态读取原追问任务，约 5 秒自动启动后台；模型仍为 Gemini 3.8 Flash / Medium，原三个有效附件仍在，合并审批仍待本人处理。当前会话缓存的旧 MCP 进程未被擅自终止；用户明确选择“稍后重连，先保留可用后台”，因此不把旧进程的冷启动称为通过。
7. 网页原两轮过程、待审阅提示和实时 `mcp-input.html` 预览继续可读。源项目未批准、合并或推送。新后台保持就绪，不需保留启动窗口。

冷启动修复后的最终全量回归 153 个测试文件 / 807 项全部通过，报告保存在本机 `.run/unified-release-20261025/final-regression.json`；独立故障恢复、实际升级记录、字节保留证明、固定入口哈希和完整发布包也在该私有忽略目录。本文的测试证据不表示手动点击过原生升级文件夹选择器；升级参数入口与实际服务链路已实测。

安装管理器只编排现有标准 release 维护接口，没有新增数据库迁移、修改自动审批、复制提供方凭据或扩大外部客户端授权。跨机器部署、连接配置生成与公开 HTTP 契约仍按后续阶段推进。
