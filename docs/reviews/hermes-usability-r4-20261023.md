# Hermes R4：日常使用流程收口

本批在用户选择统一标准 release 之后，继续补齐首个可交验收版本的人机交互。仅修改源码和静态自审，未执行类型检查、测试、构建、打包、服务操作、浏览器验收、数据迁移或真实 ACP 提示。原 R2/R3 输入清单、历史测试记录及封存包保留原样；本批单独记录当前输入，不能沿用历史签收或宣称当前页面已更新。

## 已实施的交互

| 用户情境 | 原源码问题 | 本批结果 |
| --- | --- | --- |
| 发送失败后刷新，重新打开左侧草稿 | 草稿进入普通会话，底部发送走 `/chat`，无法启动尚未分配的草稿 | 未执行且无分配的根草稿进入目标编辑器；从已存目标和专属本地草稿恢复文字，复用原 projectId/taskId，经原 record/version/负责人确认再 start |
| 切换草稿或另建任务 | 失败提交的缓存可能继续引用前一个草稿 | 切换页面清空当前提交引用；新目标与各份已存草稿分开保存；发送期间只禁用页面切换和会替换输入的示例，不限制任务执行期间浏览和补充 |
| 新空库尚无负责人 | 下拉框为空，发送后才弹出错误 | 输入前即说明连接下一步，提供打开已有成员抽屉的按钮；文字仍可先写和保存，不新增配置页 |
| 当前任务或协作成员失败/中断 | 普通失败文案，子任务只有只读状态，用户找不到下一步 | 当前轮任务树显示失败与阻塞提示、折叠错误详情、过程及成员检查入口；符合既有恢复资格的协作任务提供恢复按钮，仍调用原 resume 与目录确认 |
| 任务失败但可恢复，也可以继续提新要求 | “继续任务”和“继续追问”的区别不清 | 恢复按钮改为“恢复本次执行”；输入框说明继续原目标与发送下一轮要求的区别。暂停任务输入框明确称为“补充要求” |
| 执行中发送补充 | 显示保存的用户文字，但不知道是否已交给负责人 | 按既有指令状态显示排队数量与正在发送数量，不把 queued/claimed 当作已处理完成 |
| 任务失败、等待或停止 | 步骤条仍可能显示负责人处理中/等待汇总 | 按实际结束、阻塞和等待状态显示；草稿不再计入“进行中” |
| 请求失败 | 通用操作和发送直接显示 `HTTP ...` JSON 包装 | 解析服务端错误说明；连接中断、成员停用、并发限制、任务已执行和审批过期给出相应操作提示；没有自动重试或自动批准 |
| 预览错误提示出现 | CSS 依赖第二个 div 的位置决定哪个区域占满，新增提示会挤掉时间线 | 显式时间线容器负责伸缩和滚动；反馈面板有高度上限，保留底部输入区 |

目标编辑器只读取一次初始文字，实时内容继续由上游 GooseComposer 管理。定时快照刷新不改变 initial，不重置输入或选区。示例只在明确点击时替换新任务文字，并同步保存。开启已执行任务不会进入草稿目标编辑；服务端 record 的编辑资格与版本仍是最终依据。没有更改历史目标、调度器或数据库。

`TaskFeedback` 限于当前执行轮及其后代：完成/停止后的旧失败成员不重新显示恢复入口；只有原 `canResumeTask` 判定符合资格时才给出协作恢复按钮，后端再次核对。恢复创建执行尝试而非文件回滚。用户显式点击才调用，查看失败详情和过程不触发 Agent。

## 全目标的当前证据与统一验收

| 要求 | 当前源码证据 | 还需要的完成证据 |
| --- | --- | --- |
| 清晰创建目标和草稿续写 | `main.tsx` 的 GoalComposer、editingDraft、send；原 `draft-submission.ts` | 新候选中中文输入/选区稳定，失败后刷新续写并启动同一草稿，实际目标与负责人正确 |
| 执行状态和人工操作 | `TaskFeedback`、状态条、原审批来源隔离和决定资格 | 双成员委派/等待/审批/失败时展示正确下一步，不混会话，审批按请求判断 |
| 消息关联与继续追问 | 原会话链、`/chat` 指令/追问分流，本批保存/发送状态提示 | 执行中补充、完成后连续追问、刷新和重启后同一历史链，网络响应不明时不重复执行 |
| 取消和恢复 | 原 cancel/resume、现有恢复资格、本批协作成员恢复入口 | 当前轮取消、协作恢复、目录确认、不可恢复时不误导；符合资格且确实继续执行 |
| 错误与产物可用 | 本批错误说明，原独立预览加载器和下载 | 单个预览失败时对话/输入/审批仍可用，可重读并看到其他产物 |
| 启停、升级、备份恢复 | R3 标准 release 接入、现有锁/关闭和维护链、旧库显式停机备份 | 同一全新候选的 Windows 启停、历史保留、旧库→标准备份→新目录恢复及失败保留原件 |
| 可交用户使用的完整本地版本 | R4 输入清单、R3 构建来源、现有标准发行器 | 独立静审、统一构建/必要回归、新包输出清单、浏览器真实完整路径；当前还没有该证据 |

这张表区分源码实施和验收完成：没有将历史通过数量、新文档或静态哈希当成产品可用证据。核心 runtime、消息路由、备份格式、角色资格、权限决策和 ACP 适配未在 R4 修改；没有新表、新依赖或配置页面。

本轮只做源码阅读、`git diff --check` 与 SHA-256 核对，不新增镜像实现的简单单元测试，也不进行边界测试扩展。原有恢复、草稿、指令和会话回归仍应纳入后续必要验证；新增 UI 行为以浏览器主流程验收为准。实际模型提示仍冻结，不把旧三轮限制重新加到日常产品。

准确当前输入为 `hermes-r4-inputs-20261023.json`，以 R3 338 项清单为基线追加本批源文件与交接记录；R3 内容保持原样。本批作者自审不等于独立签收。协调任务和原独审的最新可读状态均为 idle，不能把等待意向称为正在执行的审核作业。

下一步应先独立审核 R3/R4，再进入一次统一验证。用户此前要求“先不单独测试，只做代码审核，最后统一安排测试”，本轮未自行解除该限制；独立 Agent 审核与统一运行阶段需明确授权后执行。
