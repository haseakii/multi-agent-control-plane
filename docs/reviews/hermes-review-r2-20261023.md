## P1：打开数据库前持有实际数据锁

真实与模拟入口均把数据库打开、迁移和 runtime 创建放入 `runWorkbenchInstance` 的 boot 回调。共享入口先调用既有 `acquireInstanceLock(data)`，成功后才可进入 boot；同目录的新进程在打开 SQLite 前被锁排除，端口检查不承担数据互斥。仍存活或无法确认退出的旧无锁记录会阻止进入 boot，不接管旧服务。

资源在构造前登记其清理归属，成功后按逆序关闭：HTTP 完整 drain → runtime／成员检查结束 → SQLite close → release。真实入口复用同一幂等关闭 Promise，避免 Fastify preClose 与清理栈双重停止。任一关闭失败不继续关闭其下的数据库，也不释放数据锁。既有锁删除的 token／文件身份检查保持原样，没有备用路径删除或系统权限变更。

资源构造本身使用先登记归属、再调用构造器的接口。如果 SQLite 迁移或 runtime 初始化在返回关闭句柄前抛错，无法证明内部句柄已清理时同样保留数据锁，错误保留原因为 cause；不提前释放互斥，也不修改通用存储实现。

启动检查增加原锁机制与 HTTP 关闭模块、`windows-lock-delete.cs` 依赖。原发行器已有该 C# 复制规则；统一构建须准备与 JS 同目录的原组件，本批没有准备 dist。缺文件时给出既有缺构建提示，不自动生成或安装。

## P2：停止请求绑定实例代次

在数据锁内核对旧记录，然后原子发布含 `instanceId`、PID、startedAt、starting 阶段的记录，再进入 boot。停止脚本校验 UUID、阶段和进程，写 `stop-UUID` 且内容为同一 UUID；延迟写入旧代次文件不能停止新实例。

旧无代次 stop 在发布 starting／ready 前识别并保留，新实例忽略它；不删除任何新停止请求。ready 发布前检查停止请求，发布后再次检查，之后持续监听同一代次文件。请求落在任何一侧都不会被“清理旧标记”吞掉。停止期间发布 stopping，待资源完整关闭后才退出。旧版本记录的停止协议仅保留兼容入口并确认进程退出，不声称旧服务具备新代次保障。

## P2：预览不等待快照轮询

`refresh` 只触发同步的预览状态登记，不 await 预览请求；其 pending 不再受预览 15 秒期限控制。快照呈现新内容前使旧哈希请求失效；切换会话时同步取消旧 scope，卸载取消所有请求且不再发布回调。

每个产物单独登记在途 controller、期限及请求对象身份；同一会话／ID／SHA 不重复发起。超时只失败本项，失败只在明确重读时重试。scope／SHA 改变或重读时替换请求身份，即使底层忽略 AbortSignal，迟到回调也不能覆盖当前内容。读取改用快照已存在的 sha256 字段并保留 Zod 验证，无 HTTP 或数据库模型变更。

## 待统一执行的定向场景

以下仅编写源码，没有执行：

1. 同数据目录并发启动：第二入口不能进入 SQLite／runtime 初始化；持锁至 HTTP drain、runtime、数据库均关闭，失败保留锁。
2. starting 中停止、ready 原子发布间隙停止：请求保留且正常进入清理；旧 stop 和旧 UUID 不影响新实例。
3. 旧无锁记录仍存活：新入口拒绝进入数据库初始化。
4. 慢预览期间快照／审批继续刷新，其他预览照常完成，不重复发起在途项。
5. 切换会话、SHA 改变、超时后重读、卸载：忽略迟到回调，保持单项错误隔离。

对应回归源码为 `tests/instance-lifecycle.test.mjs`、`tests/artifact-previews.test.ts`。既有三轮验收账本及其他测试记录不修改，不拿旧通过记录替代本批验证。
