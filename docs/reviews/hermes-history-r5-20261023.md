# Hermes R5：补充历史读取不再阻塞发送与状态刷新

在等待统一验证授权期间继续静态复核主流程，发现 `refresh` 在更新快照后还会等待全部轮次的 `readInstructions`；发送和追问又等待 `refresh`。因此历史读取迟迟不返回时，轮询被 pending 占住，已成功保存的发送也可能一直处于 loading。这是源码调用链发现的问题，未执行运行复现。

本批仅修改 `main.tsx` 和 `adapter.ts` 及交接说明：

- 快照刷新同步触发独立历史读取，不等待它；发送状态不再受这组历史读取请求完成时间控制。
- 当前会话和轮次列表决定读取范围，同一组在途请求复用；切换会话/轮次取消过期读取，回调按请求身份判断是否仍有效。
- 15 秒后释放历史读取的在途状态并尝试取消；后续快照可重新读取。即使取消未立即生效，旧回调也不再覆盖新范围。
- 当前范围读取失败保留已显示历史，单独提示补充记录暂未更新；不把这类失败标成整个协作引擎离线，不阻止目标/追问输入、审批或状态刷新。
- 卸载时先清除请求身份和计时器，再取消传输；部分请求失败后也取消同组剩余请求。`readInstructions` 只增加可选 AbortSignal，响应仍通过原 Zod schema 校验。

没有改变指令提交、确认送达、幂等键、任务状态、模型调用、预算或数据布局。自动重读只执行已有只读 HTTP 接口。没有新依赖、配置页面或数据库变更，没有扩展边界测试。

本轮静态核对原 R4 的 341 项输入，初始零漂移；R5 当前准确输入见 `hermes-r5-inputs-20261023.json`。旧 R2/R3/R4 清单和交接记录保持原样；当前代码仍未进入运行页面。源码自审和文件哈希不证明浏览器行为通过。
