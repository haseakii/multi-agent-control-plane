## 第一批：恢复诊断与实时快照

`collaboration_get_task` 保留现有字段，并新增 `recovery.diagnostic`：

| 字段 | 含义 |
| --- | --- |
| `version` | 当前诊断结构版本，固定为 1 |
| `reason` | 稳定的机器可读原因，不依赖解析自然语言回复 |
| `actionOwner` | 建议下一步由 operator / coordinator / runtime / none 处理；不是调度权授予 |
| `nextAction` | 查看新轮次、处理审批、等待清理、检查产物或先检查再恢复 |
| `executionActive` | 当前运行时的执行观察，不声称是 OS 级存活证明 |
| `automaticRetryAllowed` | 本批恒为 false；`failure.retryable` 不意味着副作用可安全重复 |
| `requiresWorkspaceInspection` | 中断或失败后恢复前需检查现有改动 |
| `pendingApprovalCount` | 已授权项目内、当前任务子树的待处理审批数量 |
| `observedAt` | 诊断时间 |
| `lastActivityAt` / `inactivityMs` | 可观察活动及其间隔，不是超时或卡死判定 |
| `instruction` | 静态、受控的下一步说明，不回显原始异常或凭据 |

分类优先级：已有新轮次 > 非终止任务的执行授权等待 > 正在执行/清理 > 终止状态和故障 > 等待依赖/调度 > 需要人工检查的不一致状态。`pendingApprovals.execution/review/push` 分开计数；审阅合并和推送审批不覆盖执行状态、取消或失败诊断。

网页“过程 → 执行状态”通过只读 `GET /api/tasks/:id/recovery` 获取诊断，和 MCP 网关共用运行时 `taskRecovery`。中文标题和处理说明由同一服务端生成，网页不另行解释审批或错误码。页面打开时定时刷新，切换轮次会取消旧请求，读取失败时明确显示无法获取诊断。

2026-10-24 本机补充验证：原生 Vitest 的 52 项相关测试通过（含三种执行状态下网页与 MCP 诊断一致性、合并审批不遮盖失败/运行状态、原有自动审批回归），服务端及 Hermes 类型检查通过。后续源码构建、页面查看和部署证据记录在本机隔离验证目录，不上传任务数据或凭据。本次用户授权推送优化分支；未批准任何任务合并。

完成执行不代表验收通过；必须检查实际产物、差异和测试证据。取消的任务不因再次查询而复活。

只识别已有规范错误码：CONTROL_PLANE_RESTART、ACP_CONNECTION_CLOSED、AGENT_UPSTREAM_INTERNAL、ACP_TURN_INCOMPLETE。未知错误保持通用失败。不得仅凭“没输出”或异常中的词语推断登录失效、额度不足或进程卡死。

活动时间排除查询审计、其他任务、明确属于旧 attempt 的事件、早于当前 attempt 的事件、非法或未来时间。`lastActivityAt` 仍只是观察记录，不是有用进展的证明。

## 后续切片及验收标准（尚未实现）

在现有 TaskEngine 上增加 workflow/step、依赖、预算、控制者和版本；外部协调与托管 Boss 模式显式选择。交接需比较版本、留审计记录，禁止两个协调者同时派单。服务恢复不等于自动取得继续规划权限。

### R3：结构化交接与验收

任务单携带输入产物版本、允许修改范围、验收条件和预算；独立保存执行、审查、测试和人工合并状态。审查必须指向固定差异；测试结果来自实际执行证据，不采信 Agent 自述。

验收：实现 -> 审查 -> 定向修正 -> 验证 -> 人工审阅形成闭环；新改动使旧审查失效；无测试证据时不得显示“测试通过”。

### R4：有边界的恢复和资源调度

复用本批诊断，增加持久重试预算、退避、幂等键、执行租约/代次和资源锁。账号、机器、编辑器实例、工作区是独立的约束；不把所有“retryable”错误都自动重跑。

验收：重复消息、网络断开及进程残留不导致重复副作用；额度/认证错误只由经验证的适配器信号分类；不支持强隔离的运行器必须如实报告。

### R5：界面与适配器能力证据

同一诊断服务已接到网页；后续逐步增加已验证能力及版本记录。适配器升级后重新做读取、修改、会话恢复、取消和权限测试。

验收：网页和 MCP 对同一任务给出一致原因和处理者；未经验证的能力不可冒充“可用”；过时记忆有明确替代关系与人工确认。
